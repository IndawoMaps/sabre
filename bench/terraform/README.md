# Benchmark infrastructure

Two root modules, deliberately separate, because they have opposite lifetimes.

| | `dataset/` | `box/` |
|---|---|---|
| holds | a Space with the benchmark COG | the droplet that runs the benchmark |
| lifetime | persistent | minutes |
| billing | flat monthly subscription | hourly |
| destroyed | ~never | after every run |

If they shared a module, `terraform destroy` would take the dataset with the
droplet and the next run would measure freshly generated bytes. Keeping them
apart is what lets the box be disposable.

## One-time: publish the dataset

    python3 bench/make_cog.py --out bench/data/dem.tif --size 4096 --seed 42

    cd bench/terraform/dataset
    export DIGITALOCEAN_TOKEN=dop_v1_...
    export SPACES_ACCESS_KEY_ID=...          # API -> Spaces Keys, NOT the API token
    export SPACES_SECRET_ACCESS_KEY=...
    terraform init
    terraform apply -var bucket_name=sabre-bench-yourname
    terraform output -raw sha256              # record this

Roughly 70 MB, stored twice (under `sabre/` and `titiler/`) so that pointing
`run.py --origin` straight at the Space works unchanged: it builds source URLs
as `<origin>/<server>/<file>`, and the split prefixes are what let per-server
traffic be told apart by path.

Once you have a sha256 you are happy with, put it in `expected_sha256` so a
locally regenerated COG cannot be published over it by accident. The pixels are
seeded and deterministic, but the DEFLATE encoding is whatever GDAL the writing
machine had, and a differently-compressed file has different block boundaries
and therefore different range requests. That is precisely the thing a benchmark
must hold still.

## Per run: the box

    cd bench/terraform/box
    cp example.tfvars terraform.tfvars        # ssh key name, bucket, sha256
    terraform init && terraform apply

    terraform output -raw wait_until_ready | bash
    terraform output -raw check_dataset  | bash
    terraform output -raw push           | bash

    ssh root@$(terraform output -raw ip)
    cd ~/sabre
    docker compose -f bench/docker-compose.yml up --build -d
    python3 bench/run.py --cold

Then, back on your machine:

    terraform output -raw pull_results | bash
    terraform destroy

`make_cog.py` is no longer part of the per-run path: cloud-init downloads the
published COG into `bench/data/` and checks its sha256, refusing to leave a
mismatched file in place. `push` excludes `bench/data`, so the dataset survives
repeated rsyncs.

## The hardware

`c-4-intel` — 4 **dedicated** Premium Intel vCPUs, 8 GB RAM, NVMe SSD, in the
same region as the Space.

Dedicated is the part that matters. Shared-CPU droplets (`s-*`) are burstable,
and their steal time lands in the p95/p99 columns as noise that looks like a
regression. `terraform plan` refuses to build anything that is not 4 vCPU /
8 GB, so an edited slug cannot silently change what the numbers mean.

`terraform output cost` prints the live hourly rate from the API rather than a
figure hardcoded here that would drift. Billing is hourly: a 20-minute
benchmark costs one hour.

## Where the servers read from

By default, unchanged: the local nginx origin serves `bench/data/dem.tif` over
loopback, and `run.py` parses its access log to attribute every range request
and byte to one server or the other. That accounting is the source of the
sharpest result the benchmark produces — sabre pulling ~30 requests / 25 MB
against titiler's ~867 / 1,118 MB — and nothing else reproduces it.

The Space can also be the origin directly:

    python3 bench/run.py --origin https://<bucket>.<region>.digitaloceanspaces.com

That is more like production, and it costs you the origin columns: `run.py`
reads nginx's log, and Spaces access logs are delivered asynchronously, minutes
later, far too coarse to attribute to a phase that lasted 300 ms. Use it to
sanity-check behaviour against real object storage, not to produce the
headline numbers.

## Splitting the load generator

    terraform apply -var split_load_generator=true

Adds a second droplet and an ephemeral keypair so the orchestrator on the
server box can drive `bench-client` on the generator over ssh. Both boxes join
the region's existing default VPC, which is looked up rather than created:
DigitalOcean refuses to delete a default VPC, and a VPC created in a region
that had none becomes that region's default, which would leave `terraform
destroy` permanently failing on a stack meant to be disposable. Without it,
the generator competes with the thing it is measuring for the same four cores,
which is why sabre's ~4,000 req/s `info` figure is a floor set by the client
rather than a ceiling set by the server.

    export GHCR_USER=your-github-username
    export GHCR_TOKEN=ghp_...          # classic PAT, read:packages scope

    bench/remote-bench.sh              # provision, run, leave it up
    bench/remote-bench.sh --destroy    # ... and tear it down afterwards
    bench/remote-bench.sh -- --duration 30 --suites tiles,polygon

The script does the whole cycle: apply, trust the new host keys, wait for
cloud-init on both boxes, verify the dataset, push source to each, build
bench-client on the generator, bring the servers up bound to the private
interface, run the suite, and pull the results back. It never destroys on
failure -- a broken run is when you most want the box alive -- and it prints
the destroy command on every exit so the meter is never invisible.

By hand, the same thing is:

    terraform output -raw push           | bash   # source to the server box
    terraform output -raw push_client    | bash   # and to the generator
    terraform output -raw install_client | bash   # pull bench-client onto it
    terraform output -raw bench_bind              # export before `docker compose up`
    terraform output -raw suite          | bash   # run it

### Images, not builds

Neither droplet compiles anything. CI publishes two images to ghcr.io on every
push to main, and the boxes pull them:

    ghcr.io/indawomaps/sabre-server:sha-1a2b3c4
    ghcr.io/indawomaps/sabre-bench-client:sha-1a2b3c4

That removes ten to twenty minutes from a cycle whose measured part is twenty,
and it means the thing under test was built by CI rather than by whatever
toolchain a throwaway droplet happened to have.

`remote-bench.sh` defaults the tag to the commit you have checked out, so a run
measures the code you are looking at. Override with `IMAGE_TAG`. Pin a `sha-`
tag rather than `main` for anything you intend to quote: the image tag is the
provenance, which is what ties a result to a commit even on a box with no git
checkout.

The images are private, so both droplets log in at run time with `GHCR_USER`
and `GHCR_TOKEN`. That credential is passed in from your shell and never
written to Terraform state.

It has to be a **classic** personal access token with the `read:packages`
scope — Settings → Developer settings → Personal access tokens → *Tokens
(classic)*. ghcr.io does not accept fine-grained tokens, and `read:packages`
is a classic-token scope that does not appear in the fine-grained UI at all,
so looking for it there is a dead end. A private repository also needs `repo`.

Making the packages public would remove the credential entirely: anonymous
`docker pull` works for public GHCR images, and nothing in these two images is
secret — one is a tile server whose source you are publishing anyway, the
other is a load generator. Worth revisiting if managing the token becomes more
annoying than the privacy is worth.

If a tag has not been published yet, `install-client.sh --build` still compiles
from source as a fallback.

The servers must be addressed by their **private** IP, because that is the
interface the generator can reach — `bench_bind` and `suite` both use it. The
cloud firewall opens 8787/8000/8081 to a single private /32, not to the VPC
range: another droplet on the same network has no business generating load
against a benchmark.

It is not free. Every request now carries the network between the two boxes.
That is a rounding error against a 26 ms polygon and it is the entire
measurement for a 0.3 ms `/info`, so `suite.py`:

- measures the round-trip floor (`GET /health` at concurrency 1) and prints it,
- marks any phase whose p50 lands within 3x of that floor as describing the
  path more than the server,
- and keeps `info` on a local generator regardless (`--loopback-suites`),
  because sharing cores costs it throughput while the network would cost it
  the measurement itself.

A split run and a loopback run are **not** directly comparable. `terraform
output topology` prints which one you have; it is recorded in the results too.

### The keypair

`tls_private_key` generates an ED25519 key per apply: the public half goes into
the generator's `authorized_keys`, the private half onto the server box. The
private key is therefore **in Terraform state**, which makes the state file a
secret — keep it local or in an encrypted backend. The key reaches exactly one
throwaway droplet and is replaced on the next apply.

The generator's host key cannot be known before it exists, so the server's ssh
config uses `StrictHostKeyChecking accept-new`: pinned on first contact,
refused if it changes after.

### What it costs

Splitting doubles the hourly rate: the generator defaults to the same
`c-4-intel` as the server.

That is more than it needs — `bench-client` uses roughly one core to offer
4,000 req/s. What the extra buys is the generator never being the suspect. A
smaller box is cheaper right up until the first surprising result, at which
point the first question is whether the client ran out of room, and that is not
answerable after the run. `suite.py` does record the generator's scheduling lag
every phase, so a client that cannot keep up says so — but not having to read
that column is worth the difference on a box that lives for twenty minutes.

Override with `client_size`, after checking it exists in your region:

    echo 'local.regions_for_pair' | terraform console

## Cost control

`box/` creates a droplet and a firewall; nothing else. No volumes, snapshots,
reserved IPs or backups. `terraform destroy` returns that half to zero.

`dataset/` bills a flat monthly subscription rather than per-GB, so 140 MB
costs exactly what 140 GB would. It is the price of not regenerating the
dataset, and of knowing that two runs a month apart measured the same bytes.

    doctl compute droplet list --tag-name ephemeral
